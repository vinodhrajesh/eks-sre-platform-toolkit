# EKS SRE Platform Toolkit

A reference build of the reliability platform I run in production, rebuilt here as a public,
portfolio-ready toolkit: Terraform-provisioned EKS, Karpenter autoscaling, GitOps-style Kubernetes
manifests, centralized observability, and an AI-based self-healing agent for automated fault
remediation.

**Built mostly with AI coding agents** (Cursor) — every Terraform plan and Kubernetes change in
this repo was generated by an agent and reviewed by a human before merge, using the plan-review
guardrail in [`agent-ops/`](agent-ops/). That workflow — propose with an agent, gate with a human —
is the same one I use day-to-day on production infrastructure.

## Why this exists

Most "DevOps portfolio" repos are a pile of unrelated snippets. This one is organized the way a
real platform is: one cluster, one autoscaling story, one observability stack, one on-call
runbook set, and two real incidents that shaped the design decisions below. Every module exists
because something broke in production without it — see
[`docs/incident-postmortems/`](docs/incident-postmortems/).

## What's inside

| Path | What it is |
| --- | --- |
| [`terraform/`](terraform/) | Modular, reusable IaC for EKS, Karpenter, ECR lifecycle policies, and the observability stack, split into `staging` / `production` environments |
| [`kubernetes/`](kubernetes/) | Environment-overlaid manifests: resource quotas, `LimitRange`, `PriorityClass`, `PodDisruptionBudget`, and KEDA `ScaledObject` configs |
| [`apps/self-healing-agent/`](apps/self-healing-agent/) | A Python agent that watches the cluster for `CrashLoopBackOff`, `OOMKilled`, and node-pressure events, remediates automatically, and posts a summary to Slack |
| [`agent-ops/`](agent-ops/) | Guardrails for using coding agents safely on infrastructure: a Terraform plan-review gate that blocks destructive changes on protected resources without a named human approver, plus a runbook-triage agent for on-call |
| [`docs/incident-postmortems/`](docs/incident-postmortems/) | Blameless postmortems for the two production incidents this platform was built to stop from recurring |
| [`.github/workflows/`](.github/workflows/) | GitOps-only CI: `terraform plan` runs on every PR, `apply` requires a manual approval gate — no click-ops, no ad-hoc `kubectl` in production |

## Architecture

```
Akamai → CloudFront → ALB/NLB → EKS (GKE/any-cloud-equivalent)
                                   ├── API + worker pods (resource-limited, PriorityClass'd)
                                   ├── KEDA-scaled queue workers
                                   ├── self-healing-agent (DaemonSet-adjacent watcher)
                                   └── kube-prometheus-stack + Loki + Promtail
                                           └── alerts → PagerDuty / Slack ChatOps
```

See [`docs/architecture.md`](docs/architecture.md) for the full breakdown, including how the
observability stack maps alerts to root cause rather than symptom.

## Running it

```bash
# 1. Review the plan — never apply blind
cd terraform/envs/staging
terraform init
terraform plan -out=plan.out

# 2. Run the plan through the agent-ops guardrail before anyone applies
python ../../../agent-ops/terraform_plan_guardrail.py plan.out --approver "<your-name>"

# 3. Apply only after the guardrail passes and a human has reviewed the PR
terraform apply plan.out
```

```bash
# Build and run the self-healing agent locally against a kind/minikube cluster
cd apps/self-healing-agent
docker build -t self-healing-agent:local .
docker run --rm -v ~/.kube/config:/root/.kube/config self-healing-agent:local
```

## Publish to GitHub

This folder already has a `main` commit. Create an empty public repo named
`eks-sre-platform-toolkit`, then:

```bash
git remote add origin git@github.com:YOUR-USERNAME/eks-sre-platform-toolkit.git
git push -u origin main
```

Replace `YOUR-USERNAME` on the resume contact line so it matches.
